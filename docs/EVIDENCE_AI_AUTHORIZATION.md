# Evidence image access and re-analysis

Police access is derived from the current linked incident: the authenticated user's ID must equal the incident's `investigatingOfficerId`, or appear as `officerUserId` in `response_unit_members` for the incident's current `assignedUnitId`. A report-only link resolves through the report's `incidentId`. Missing records and conflicting report/incident links are denied. Station and role alone do not establish access. Admin access and a citizen's own-report evidence access retain their existing policy.

`POST /api/video-evidence/:id/reanalyze` requires an authorized operator and a reason of 5–300 characters. It creates a new analysis rather than replacing history. Repeated calls to the initial analysis endpoint are rejected. An existing unresolved observation with the same image hash, context, model, version, threshold and detections is reused; a completed human review is not overwritten. PostgreSQL serializes these operations using the existing transaction advisory lock. The evidence analysis, observation and successful audit entries share the existing transaction.

Analysis and re-analysis failures with a recognized application status are recorded as failed audit events; database transaction failures can roll back those events as well. Analysis history is available through `GET /api/video-evidence/:id/analyses` and individual runs through `GET /api/video-evidence/:id/analyses/:analysisId`, subject to the same evidence authorization.

Known limitation: a failed AI request is represented by its audit events, not by a failed row in the analysis history. A database failure can also leave no failure audit because the required writes roll back together. There is currently no separate post-rollback audit transaction; consequently operators cannot rely on the database audit trail alone to account for every persistence or commit failure. An HTTP error remains the result, and successful analysis, observation, and audit writes remain atomic.
